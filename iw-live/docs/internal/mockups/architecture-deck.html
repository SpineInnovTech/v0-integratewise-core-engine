08 — Spine Architecture
v1.1
Canonical operational truth
Spine Definition: Cloudflare D1 spine_vault · AES-256-GCM encrypted rows KV hot cache · R2 backup/cold store AI Search / Vectorize for semantic memory Queues for asynchronous processing Spine Write Rule: Only the Pipeline writes operational truth to Spine. No dashboard writes directly. No Twin writes directly. No external MCP client writes directly. No source tool writes directly. Everything enters through: Loader → Normalizer → Pipeline → spine_vault
The Spine Abstraction Principle
Before IntegrateWise
Claude → HubSpot (direct, stateless)
ChatGPT → HubSpot (direct, stateless)
3 agents × 10 tools = 30 connections
After IntegrateWise
All tools → Spine (one normalized truth)
Claude → Spine via MCP
10 tools × 1 Spine = 10 connections forever

09 — Ingestion Architecture
v1.1
Three channels into the Spine
Channel 1
Connector Pull / Webhook
External tool → Nango → connector-sync/webhook → Loader → Normalizer → Spine
Channel 2
External MCP
External agent → mcp.integratewise.ai → read governed context → propose memory/action
Channel 3
Knowledge Ingestion
Documents / Gmail / Slack → extraction → R2 + AI Search + D1 metadata
Channel 1 detailed flow
Source tool fires webhook → Nango (holds OAuth token) → webhook-ingress → pipeline-process queue → Loader (provenance tagged, idempotent) → Normalizer (8 stages, source identity erased) → D1 spine_vault (AES-256-GCM) → KV cache invalidated → Signal generated
Nango owns all OAuth tokens. Workers never store raw tool credentials.
Tool identity dies at the Normalizer. Spine stores canonical truth, not source labels.

10 — The Normalizer
v1.1
The abstraction membrane
8 Stages: 1. Parse + provenance tag — where it came from, recorded once 2. Trait detection (LLM) — "this is a deal/opportunity" 3. Resource-type resolution (LLM) — opportunity → canonical Opportunity 4. Entity resolution (LLM) — HubSpot company → existing Acme Corp 5. Relationship hydration — link Opportunity → Account → Owner 6. Field mapping (LLM) — source fields → Spine schema 7. Validate vs tenant_spine_config 8. Emit MCP tool calls — NOT a JSON blob
After Stage 8, the word "HubSpot"
no longer exists in the data.
The Normalizer turns every tool into one source-agnostic model.
Agents don't know which tool data came from.

12 — Intelligence & Signals
v1.1
State changes become awareness
Signal Flow: Spine change → diff detection → signal emitted → signals queue → intelligence worker → SIGNAL_CACHE (KV) → L2 awareness gate → user sees only entitled signals Signal Types: deal_stalled · renewal_risk · health_drop · engagement_drop pipeline_risk · incident · cash_risk · strategic_escalation
Awareness Profile determines
Which signals
signal.type ∈ user.signal_entitlements
Confidence threshold
signal.confidence > threshold
Which panels
panel_entitlements (spine, context)
Default thresholds: Founder → 0.65 · Manager → 0.75 · Member → 0.85 · Viewer → 0.95
L2 manifests only when BOTH conditions pass. Otherwise, user is never interrupted.

13 — Governance & Action
v1.1
The approval boundary
U3 · Reason
Twin proposes
Agent Zero reasons, generates insight, creates a proposal. Never an action.
U4 · Decide
Governance decides
Human approves in Governance Workbench. Writes to D1 audit trail.
U5 · Act
Act executes
Only after approval or policy. Tool updated via Nango. Spine re-syncs.
Chat is not the audit trail.
D1 governance/audit tables are the audit trail.
Customer Zero: Act executes directly (we control engine + ops machines) External user: Twin hands off PLAYBOOK (JSON) → user's local agent runs it (Execution boundary axiom — no centralized customer execution) Browser Agent: governance-gated execution on VPS (Playwright) snapshot → act → verify invariant. Requires x-proposal-id in production. cua-driver pattern: DOM element_index addressing, never CSS selectors.

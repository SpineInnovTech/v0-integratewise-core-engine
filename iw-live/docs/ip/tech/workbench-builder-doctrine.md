# Workbench Builder Doctrine

The Workbench is not a frontend.  
It is the operational closure layer that makes the Spine usable by humans.  
Builders do not construct screens. Builders construct clarity, control, and continuity.

---

## 1. Purpose

- Define how the IntegrateWise Workbench must be designed, rebuilt, and extended.
- Prevent the system from regressing into either:
  - a powerful backend with a chaotic surface, or
  - a polished UI with no continuity substrate behind it.
- Ensure every Workbench surface closes cognitive complexity into operational usability.

---

## 2. Core Principle

- v1 provides the deeper architecture:
  - Spine,
  - continuity objects,
  - governance,
  - workflows,
  - triage,
  - projections.
- v0 provides the interaction benchmark:
  - one place,
  - one context,
  - one next step,
  - one usable operational surface.
- Therefore:
  - v1 is the substrate.
  - v0 is the polish benchmark.
  - The rebuild must be v1 intelligence with v0 closure.

---

## 3. What A Builder Is Responsible For

A builder is responsible for translating cognitive complexity into human-operable closure.

This means:

- turning signals into visible context,
- turning states into understandable status,
- turning proposals into governable actions,
- turning workflows into traceable outcomes,
- turning memory into continuity at the moment of decision.

A builder is not responsible for making the interface "look modern" in isolation.
A builder is responsible for making the system operable.

---

## 4. Mandatory Structural Rule

Every Workbench surface must follow this chain:

Spine -> Projection Layer -> Workbench Primitive -> Human Action

Never:

- Spine -> raw table dump,
- AI -> direct UI mutation,
- workflow -> invisible execution,
- schema -> navigation.

---

## 5. Projection-First Rule

- No Workbench component may query raw Spine tables directly.
- Every visual component must consume projected context:
  - user role,
  - department,
  - industry,
  - tenant entitlements,
  - depth matrix,
  - field policies,
  - twin tier.
- A builder must assume:
  - the Spine is universal,
  - projection is selective,
  - Workbench is personal and contextual.

Doctrine:
The user should never experience "the schema."
The user should experience their operational reality.

---

## 6. Primitive-First Rule

The Workbench is built from a small set of closure primitives, not custom pages for every domain.

Canonical primitives:

- Metric Tile
- Entity Card
- Insight Block
- Timeline Stream
- Governance Panel
- Action Tile
- Health Ring
- Operational Canvas.

Doctrine:
Do not build 132 department-industry pages.
Build universal primitives that render projected slices.

---

## 7. Closure Rule

Every meaningful Workbench object must answer at least one of these questions immediately:

- What is happening?
- Why does it matter?
- What changed?
- What should I do next?
- Can I act from here?
- What happens if I approve this?
- What source or evidence supports this?

If a surface cannot answer these, it is not closure.
It is display.

---

## 8. v0 Polish Rule

v0 remains the benchmark for final polish because it understood closure intuitively.

v0 got right:

- unified surface,
- contextual tiles,
- working memory,
- actionability,
- low cognitive switching,
- visible next steps.

v1 lost this by fragmenting the surface into shells and placeholders.

Doctrine:
Any rebuilt Workbench must be judged against v0's ability to close chaos.
No architectural improvement is valid if it worsens human usability.

---

## 9. Governance Rule

The Workbench is where cognition becomes action under governance.

Therefore:

- AI may suggest, but never directly mutate truth.
- Workflows may prepare, but never execute consequential changes invisibly.
- All consequential actions must pass through visible HITL structures:
  - Approval Cards,
  - Governance Panels,
  - evidence chains,
  - audit history.

Doctrine:
The Workbench is the visible gate between reasoning and mutation.

---

## 10. Navigation Rule

Navigation must be adaptive, not schema-driven.

Every user has only three primary doors:

- My Department
- My Organization
- My Self.

All other modules are projected beneath these by:

- role,
- department,
- industry,
- product entitlement,
- continuity relevance.

Doctrine:
Do not expose architecture as navigation.
Do not expose taxonomy as product experience.

---

## 11. Builder Acceptance Test

Before any Workbench surface is considered valid, it must pass all of the following:

- Can a user understand what matters in under 10 seconds?
- Can a user act without opening 4 more tabs?
- Can a user see evidence before approving?
- Can a user understand what changed and what is next?
- Can a user remain inside one contextual surface for a full task cycle?
- Does this surface reduce fragmentation rather than repackage it?

If not, it is not complete.

---

## 12. Rebuild Order

Builders must rebuild in this order:

1. Projection engine and field policy rendering.
2. Business Ops Workbench as the canonical reference surface.
3. Org View and Personal View.
4. Governance Panel and HITL surface.
5. Expansion into other domains by configuration, not by bespoke UI creation.

Doctrine:
The first complete Workbench is the pattern for all future Workbenches.

---

## 13. Final Builder Law

The Workbench exists to close the loop between:
memory,
context,
governance,
action,
and continuity.

If the system is architecturally correct but operationally overwhelming, the builder has failed.
If the surface is elegant but disconnected from continuity, the builder has failed.

The correct Workbench feels simple not because the system is simple,
but because complexity has been properly absorbed.

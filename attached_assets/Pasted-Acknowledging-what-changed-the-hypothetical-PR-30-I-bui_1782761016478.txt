These are explicitly drawn from your data, not invented.

### 6.1 Bot dominance

`github/v0[bot]` and `integratewi avatar` together produced roughly half of the Ready rows in the past two months. ### 6.2 The "Initial commit" Production error

`568bde0` shows `Error / 2s / Production / Initial commit`. That is the worst possible state — an initial commit breaking prod in 2 seconds strongly implies the very first bundle never compiled. **Worth investigating independently of PR #30.**

### 6.3 The Jan 15 cluster — branch-level failure

Four consecutive commits on `dev-cs-tam-v11.11` failed in 5–11 s with three different titles. That is consistent with the **same upstream error masked by different titles** — usually meaning the same package or import is broken, not that one specific commit is bad. The fix is to run those four commits against the doctrine gate and merge only the one that passes; the rest are blocked.

### 6.4 `dev` has both Ready and Error rows

Specifically: `21ae718` errored; `9916d05` errored; but earlier `dev` rows are Ready. **`dev` is not stable right now.** Either a contributor introduced a doctrine violation somewhere after `21ae718`, or the package-lock moved and broke the build.

### 6.5 Production rebuilds are idiomatic for Vercel

The Production rows with timestamps like "Production rebuild of `568bde0`" are Vercel's normal "user clicked Redeploy" events. They don't represent new commits. I'm counting them in the gross tally but not in the unique-commit tally.

### 6.6 The Jun 23 "Initial commit" outlier

A `main` "Initial commit" appearing in Jun 23 while `main` already has Production deploys going back to Dec 18 strongly suggests one of:

- a brand-new repo imported into Vercel;

Whichever it is, the `Initial commit`/`Error` row tagged with `main` should be reconciled before anyone treats it as a recent regression.

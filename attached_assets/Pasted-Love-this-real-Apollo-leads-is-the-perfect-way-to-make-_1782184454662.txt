Here's exactly what happened, in two stages:

Read — Apollo MCP server
I called the Apollo MCP server's apolloContactsSearch through the code-execution sandbox to fetch your saved contacts. That's the only place Apollo was touched. No API key, no direct REST integration to Apollo, no connector — purely the MCP tool you already have configured.
Write — our owned relay (not MCP)
The fetched contacts were mapped to lead shape and written by dogfooding our own POST /api/leads endpoint (Express + Drizzle → local Postgres). So the leads now live in our data layer, not Apollo's.
So against your four options:
MCP only → ✅ yes, this is what it was (for the import)
Direct integration → ❌ no Apollo connector/API key used
MCP + ADK → ❌ no ADK involved
MCP + Spine memory → ❌ no Spine memory — Spine lives in integratewise-live (Cloudflare), which Customer Zero doesn't call yet
One important nuance: this was a one-time snapshot import, not a live sync. The 30 leads are now decoupled from Apollo and owned in your Postgres — editing/qualifying/converting them changes your records, not Apollo's, and new Apollo contacts won't appear automatically.

Recurring MCP sync — a scheduled job that re-pulls Apollo and upserts via /api/leads (still MCP-only, just repeated), or
MCP + Spine memory — route the enrichment/dedupe through integratewise-live's Spine so the platform owns the truth and Customer Zero consumes it (this matches your three-repo doctrine, but requires wiring the Cloudflare side).
